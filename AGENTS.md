# AGENTS.md — Wiki Schema for this Knowledge Base

This file is the **schema** layer of the LLM-wiki pattern. It tells an LLM (or
any agent) how to ingest sources, answer queries, and maintain the wiki so the
knowledge base stays consistent and OKF-conformant. Co-evolve it as you learn
what works.

## Format: OKF v0.2

Every wiki page is an OKF concept: a UTF-8 markdown file with a YAML frontmatter
block delimited by `---`. The only required key is `type`. Always include these
when known:

- `type` — Concept | Entity | Source Summary | Analysis | Reference | Playbook
- `title` — human-readable name
- `description` — one sentence
- `tags` — list of short strings
- `status` — draft | stable | deprecated (default stable)
- `generated: { by: <actor>, at: <ISO8601Z> }` — who/what wrote it
- `verified` — list of `{ by, at }` confirmations; use `human:<id>` when a
  human confirmed (yields human-reviewed trust tier)
- `stale_after` — absolute ISO-8601 instant if the content can go stale
- `sources` — list of `{ id, resource, title, author?, usage_count?, last_modified? }`

Actor convention: `human:<id>`, `<agent>/<version>`, `process:<id>`.
Per-claim attribution: markdown footnote `[^id]` keyed to a `sources[].id`.

Reserved filenames (never use for concepts): `index.md`, `log.md`.

## Directory layout

- `raw/` — IMMUTABLE source material (you read, never edit). Put new sources here.
- `templates/` — skeleton pages (concept, source, analysis, entity). MANDATORY
  starting point: copy the matching template and fill it in; do not invent your
  own frontmatter keys or section order.
- `wiki/index.md` — content catalog, regenerated by `tools/okf.py rebuild-index`.
- `wiki/log.md` — change history, newest first, grouped by date.
- `wiki/overview.md` — orientation page.
- `wiki/sources/` — one summary page per ingested source.
- `wiki/entities/` — people, orgs, tools.
- `wiki/concepts/` — ideas, methods, patterns.
- `wiki/analyses/` — comparisons, syntheses (often answers written back).
- `wiki/references/` — external material / run instructions / code.

## Workflows

### Ingest
1. **Dedupe first**: read `wiki/index.md` and search the bundle for existing
   pages on this topic. If one exists, EXTEND it — never create a sibling page
   covering the same topic (that is how vaults accumulate near-duplicates).
2. Read the new source in `raw/`.
3. Copy the matching template from `templates/` and write
   `wiki/sources/<slug>.md` summarizing it (with provenance).
4. Update relevant `wiki/entities/`, `wiki/concepts/`, `wiki/analyses/` pages;
   add cross-links (use `/`-prefixed bundle-relative links).
5. Update `wiki/index.md` (or run `python3 tools/okf.py rebuild-index`).
6. Append entries to `wiki/log.md` in the fixed format below.

### Update (amend vs. supersede)
- **Amend** when the page is right but incomplete: edit it, add claims with
  attribution, bump `generated.at`. Keep the old content if still correct.
- **Supersede** when the page is wrong or fundamentally restructured: create the
  new page, set the old one to `status: deprecated`, and add
  `superseded_by: <new page path>` to its frontmatter (plus a link at the top
  of the body). Never silently delete a page that other pages link to.
- Either way, log the change in `wiki/log.md`.

### Query
1. Read `wiki/index.md` first; drill into relevant pages.
2. Synthesize with citations. If the answer is durable, file it as a new page
   (use `templates/analysis.md`).

### Lint (run `python3 tools/okf.py lint`)
Check for: missing `type`, orphan pages (no inbound links), broken links,
stale concepts (`now >= stale_after`), contradicting claims, missing
cross-references, missing `## Summary`, oversized pages, bad filenames.

### Log format (`wiki/log.md`)

Machine-readable, one line per action, newest first:

    YYYY-MM-DD | ACTION | path | free-text note

- ACTION: `create` | `update` | `deprecate` | `delete` | `ingest` | `rebuild` | `maintenance`
- path: bundle-relative (`wiki/concepts/foo.md`, `raw/foo.pdf`, `.` for vault-wide)
- Free-text note: single line, no pipes (escape as `/` if unavoidable).
- The format header must stay at the top of the file so agents can re-read it.

## Principles
- The wiki is a compounding artifact; never discard a good answer into chat.
- Prefer structured markdown (headings, tables, lists) over prose.
- Record provenance and verification honestly; mark unverified as such.

## Anti-hallucination rules (hard constraints)

- **Never cite a source that does not exist** in `raw/` or in the page's
  `sources[]` frontmatter. If you cannot attribute a claim, do not write it
  as fact — write it with an explicit *(unverified)* marker or leave it out.
- **Never invent frontmatter values**: `generated.at` is the real UTC
  timestamp of when you wrote the page; `verified` entries only when a real
  actor actually confirmed it.
- **Unsure = draft**: if any claim on a page is unverified, the page gets
  `status: draft`, never silent confidence.
- **Summarize what the source says**, not what you expect it to say. If the
  source file is missing from `raw/`, say so — never reconstruct content
  from memory.
- **Contradictions are content**: if a new source contradicts an existing
  page, do not average them — record the contradiction explicitly (see
  `templates/analysis.md`).

## Writing rules (enforced by `tools/okf.py lint` where marked)

- **Head-first summary**: the body must START with `## Summary` containing one
  paragraph that makes the page understandable on its own. Agents frequently
  read only the head of a page; the core claim goes there, details below.
  [LINT: missing-summary]
- **Page length cap**: prefer < 300 lines; split the page if it exceeds that.
  Long pages rot — citations and link integrity decay. [LINT: page-too-long]
- **Filename conventions**: kebab-case ASCII slugs only (`my-topic.md`, never
  `My Topic.md`); no dates in filenames (dates live in frontmatter); no spaces
  or non-ASCII characters. Renames break cross-links. [LINT: bad-filename]
